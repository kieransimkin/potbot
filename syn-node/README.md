# SYN standalone local node — Phase 43 service + Phase 44 Python HD authority

This is an **independently installable** `syn-node-service` Python package. It is
not imported by Potbot. It implements the **real Linux Unix-socket transport**
for Potbot's Phase 42 read-only local protocol: peer credentials, challenged
Ed25519 public attestation, and adoption-receipt retrieval. It also implements
OS-CSPRNG creation and **OS credential store** custody of *temporary agent
Ed25519 keys* (when a verified native OS keyring backend is available).

**Phase 44 Python operator profile.** SYN now includes an optional **Python**
CIP-3/Ed25519-BIP32 V2 operator key-store implementation using pinned
`pycardano==0.19.2`, true OS CSPRNG installation entropy and the native
OS credential backend. It derives root `m/6969'/420'`, base
`m/6969'/420'/0'/0/0`, and eight root-derived candidate public keys.
See `docs/implementation/44-syn-python-hd-operator-keystore.md`.

**Still not a production identity issuer without real-host qualification.**
Operator root/base keys are the distinct
Ed25519-BIP32 V2 derivatives `m/6969'/420'` and
`m/6969'/420'/0'/0/0`. A raw 32-byte Ed25519 seed cannot replace an
Ed25519-BIP32 extended private key. The Python v2 profile can now create keys and
derive public candidates when
its pinned optional library and OS keyring are installed. The v1 native-signer
configuration remains available for previous deployments. A provider preflight
without a real cross-language vector and OS-keystore qualification is not
permission to activate an agent or use production keys.
There is no fallback to Potbot's legacy encrypted file vault.

## Install and run

For new operator installations use the SYN-owned Python HD profile:

```bash
python -m pip install -e './syn-node[hd]'
syn-node new-operator --keyring-service syn.operator --keyring-account operator-1 \
  --lock-dir /absolute/private/syn-locks
```

Then create a version-2 private daemon config with `keyring_service`,
`keyring_account`, the returned `expected_base_public_key_hash`, `socket`,
`registry`, `receipt_db` and `mode: "operator"`. See the Phase 44 document for
an exact example. The old v1 `native_signer_executable` config below is
**legacy/optional**, not required for new Python SYN operator installations.

Install separately into a SYN-owned environment, with the packages required in
`pyproject.toml`. Do not import from a Potbot sandbox. The operator provisions
private `0700` directories for configuration, socket, ledger and registry.
Configure a `0600` canonical JSON file (single line, lexicographic key order):

```json
{"expected_base_public_key_hash":"<64 lower-hex digits>","mode":"operator","native_signer_executable":"/absolute/path/to/pinned/syn-native-sign","native_signer_sha256":"<64 lower-hex digits>","receipt_db":"/absolute/private/receipts.sqlite3","registry":"/absolute/private/syn-installations.json","schema_version":1,"socket":"/absolute/private/syn-operator.sock","type_ref":"synny://type/syn-local-service-config-v1"}
```

The socket directory and registry parent should be separate owner-private
folders. The receipt journal contains **only public signed packets** and no
hardware unique identifiers, entropy, chain codes or private keys.

```bash
syn-node preflight --config /absolute/private/operator.json
syn-node serve --config /absolute/private/operator.json
# Explicit, operator-only import of an independently completed public receipt:
syn-node publish-receipt --config /absolute/private/operator.json --receipt /absolute/private/adoption.json
# Agent-mode *temporary* signing key, generated by OS CSPRNG, stored in OS keyring:
syn-node new-agent-temporary-key --keyring-service syn.agent --keyring-account <agent-uuid> --lock-dir /absolute/private/agent-locks
```

`preflight` confirms local protocol and pinned signer replies; it does NOT mark
CIP-3, hardware custody, secure adoption or production isolation qualified.
The actual HTTP/P2P transport, hardware attestation, signed pulse broadcast,
private-key migration, inherited-key derivation and live agent adoption remain
separate gates. A stored operator receipt is a verified signed *claim*, not
independent evidence of exclusive agent keystore custody.

## Native SYN signer protocol, proposed version 1

The SYN-owned external program is operator-pinned by absolute executable path
and SHA-256. It reads exactly one canonical JSON request on stdin:

`{"method":"public|sign","payload_hex":"<hex bytes or empty>","schema_version":1,"type_ref":"synny://type/syn-native-keystore-sign-v1"}`

and returns bounded canonical JSON with keys `schema_version=1`,
`type_ref="synny://type/syn-native-keystore-sign-result-v1"`,
`method`, `public_key` (raw Ed25519 verification key as 64 hex digits) and
`signature` (128 hex digits for `sign`; `null` for `public`).

The native signer **must** validate its own operator key type, derivation and OS
keystore pin. Public signer binding, request signatures and process exit status
are checked independently by this service. No private bytes or key export
method exists in the transport. Source pinning is not binary attestation; the
host must qualify native custody independently.

## Test gates

```bash
PYTHONPATH=syn-node/src:src python -m pytest -q syn-node/tests \
  tests/unit/test_syn_local_daemon.py tests/unit/test_syn_adoption.py
```

The service tests use disposable **test-only** signers; they establish wire
compatibility, signed response verification, replay-safe public-receipt storage,
strict input bounds, registry privacy and agent-temp key generation. They do not
claim OS keyring qualification, CIP-3 native derivation or P2P interoperability.

On Windows/macOS the local client needs a separately qualified named-pipe/XPC
transport. Linux Secret Service, macOS Keychain and Windows Credential Manager
must be opened through their explicit native `keyring` backend; fallback
plaintext storage is rejected. A service process using ordinary Python memory
cannot claim memory-locking or hardware-backed non-exportability.

## Phase 45 — explicit operator recovery and qualified-provider gate

Phase 45 adds a 24-word BIP-39 export/recovery workflow, pinned
`cbor2==5.8.0` / `cbor2pure==5.8.0` / `pycardano==0.19.2` compatibility,
and a public-only signing smoke. This does **not** add a private key export or
signing capability to the local service socket. Use `syn-node show-recovery`
only from a physical/private controlling terminal, with session recording off.
`recover-operator` requires the independently pinned original base hash and
an **empty** destination OS keystore; it cannot overwrite partial installs.
See [`docs/implementation/45-syn-python-recovery-and-provider-qualification.md`](../docs/implementation/45-syn-python-recovery-and-provider-qualification.md).

```bash
syn-node show-recovery --keyring-service syn.operator \
  --keyring-account operator-one --expected-base-public-key-hash "$PINNED_BASE_HASH"
syn-node recover-operator --keyring-service syn.operator \
  --keyring-account new-destination --lock-dir /absolute/private/syn-locks \
  --expected-base-public-key-hash "$PINNED_BASE_HASH"
syn-node qualify-operator --config /absolute/private/operator.json
```

A functional smoke is not independent hardware custody certification or secure
inherited-key adoption. Do not feed recovery words into Potbot, agents, CI,
command arguments, environment variables, files or service logs.
