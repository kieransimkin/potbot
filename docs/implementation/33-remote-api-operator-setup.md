# S8 — Remote API setup: operator vault, backend and frontend

## Credential architecture

Potbot has five built-in hosted-model providers: OpenAI, Anthropic, Gemini,
xAI and EvoLink. Use the **existing** `CredentialStore` native keyring backend,
`POTBOT_CREDENTIAL_PROFILE` and `ServiceCredentials`; do not introduce another
filesystem/DB/guest secret store. A credential is operator-profile-scoped, not
per-agent or per-workspace. Each API request additionally requires a registered
workspace bearer validated through the existing authenticated DB transaction.
A `providers.*` credential is never returned by the backend or Next.js proxy.

Two **different** capabilities are required:

1. The existing workspace bearer authenticates the workspace and principal.
2. A separate `api.setup_token`, generated by the operator and saved to the
   native keyring, authorizes management of provider credentials. Next.js holds
   its copy server-side as `POTBOT_UI_SETUP_TOKEN`; it is never returned in
   browser hydration or API responses. An ordinary `POTBOT_UI_BACKEND_TOKEN`
   alone is insufficient to read provider setup status or replace a key.

Configure the setup capability from an interactive terminal:

```powershell
# Generate a strong random token locally, then copy it into your password manager.
# Or enter an existing strong >=32-character high-entropy secret.
.\start.ps1 credentials service-set --name api.setup_token
.\start.ps1 credentials setup-show
```

Set the exact returned setup token as `POTBOT_UI_SETUP_TOKEN` in the **Next
server-only environment**, and restart that Next server. Do not prefix it with
`Bearer `, put it in `NEXT_PUBLIC_*`, commit it to `.env`, pass it in URL
parameters, or store it in `/etc/ai`. The backend resolves only the vault copy.
The operator has to supply it separately to the Next server; no automatic key
exchange, vault read by a browser or bootstrap-key display is provided.

Existing providers can still be configured headlessly by their approved
`*_API_KEY` environment variables. A nonempty environment override takes
precedence over the native vault and is deliberately **read-only** on the
setup page: saving/removing a vault key wouldn't change the effective runtime
value. Move that key out of the environment for native-vault management.

## Backend endpoints (loopback `potbot serve`)

All endpoints below require both `Authorization: Bearer <workspace bearer>`
and `X-Potbot-Setup-Token: <setup capability>`. Mutations also require the
operator Next server's exact allowlisted `Origin`. They return
`Cache-Control: private, no-store`, never the secret, and never provider error
bodies. The route is *not installed* on a nonloopback listener.

| Method | URI | Contract |
| --- | --- | --- |
| GET | `/v1/ui/setup/apis` | `potbot-api-setup/v1`, 5 provider records, effective source, status and vault editability |
| PUT | `/v1/ui/setup/apis/{provider}` | `{ "key": "...", "confirm": true, "replace": false }`; rotation requires `replace: true` |
| DELETE | `/v1/ui/setup/apis/{provider}` | `{ "confirm": true }`; no shared provider state is modified on an env override |
| POST | `/v1/ui/setup/apis/{provider}/test` | `{ "confirm": true }`; explicit metadata-only GET to the fixed provider catalog origin |

Provider path segments are exact allowlisted identifiers; no arbitrary remote
URL, arbitrary credential name or JWT/OAuth token exchange is accepted. Native
vault operations use the credential store's verified read-after-write semantics.
Stored keys are never exposed, including last-four previews. `probe` is a
connection/read check, **not** approval for model generation: the separately
configured disclosure, model and budget policy still governs actual usage.
Provider errors are converted to bounded categories without their response text.

The Next.js bridge under `/api/ui/setup/apis` requires the existing signed
operator session cookie, exact mutation Origin/CSRF checks, a configured
workspace connection and the server-only setup capability. It validates and
projects provider records and never proxies provider-API raw errors. The page
is `/setup/apis`, also linked from the UI menu and Preferences panel. Keys
are kept only in ephemeral React form state during input and cleared after a
successful operation, never in localStorage, a URL or a persisted preference.

## Qualification and security limits

- Integration tests verify unknown provider, vault unavailable, duplicate JSON
  fields, invalid secrets, rotation confirmation, env overrides, missing setup
  token, workspace authentication, Origin, bounded request and no response leak.
- The test endpoint uses the existing `HostedProviderClient.list_models`, whose
  fixed origins, no proxies/redirects and request/response limits are preserved.
  It is an *opt-in external request*. It can be rate-limited by providers and
  may require provider permissions for model listings.
- The setup token is operator-global for one vault profile. Keep the Next app
  and Potbot API bound to loopback behind an authenticated TLS frontend if
  exposing the UI remotely. Do not expose the raw setup API on public HTTP.
- The model catalog's per-process cache is invalidated on a native vault change
  in the current service. Other API workers retain their old metadata until
  their existing five-minute TTL expires; model usage still re-resolves the
  key and rechecks policy at execution.
- Multiple mutually untrusted users should **not** share this setup token or
  the current single-operator UI cookie. Production per-user admin RBAC,
  distributed throttling, durable no-secret audit events, separate tenant
  credential profiles, OAuth consent flows and encrypted replicated vaults
  require a separate security qualification.

## Tests

```bash
uv run --locked pytest -q tests/unit/test_ui_api_setup.py
cd frontend && npm test && npm run typecheck && npm run build
```

These are operator/source acceptance commands. A mocked vault does not prove
Windows Credential Manager, macOS Keychain or Linux Secret Service access on
the actual production user account.
