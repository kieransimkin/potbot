# S5 — Shared tools: read-only execution and operator-unlocked per-tool maintenance writer

**Scope:** the existing `/usr/local/tools` store and the `SharedToolStore` approval/cleanup workflow are authoritative. This increment closes the ordinary-execution write mount that previously let an unbrokered Bash process change any shared tool. Tools remain physically shared and group-writable only while a trusted maintenance writer is admitted.

**Canonical policy decision, 1 November 2026:** read-only is the normal state. An agent does not gain shared-tool mutation authority from group membership, the `Tools` symlink, a shell, or the existence of an executable. A shared-tool mutation requires an explicit operator unlock implemented as a scoped `ToolWriteGrant`. The unlock is tied to one tool and one exclusive maintenance lease, lasts only for the supervised maintenance operation, and must be revoked on every terminal path before ordinary execution resumes.

- Normal interactive shells and tool executions see `/usr/local/tools` through an **OS read-only bind mount**. The `/home/<agent>/Tools` symlink continues working and does not grant write permission.
- Only an operator-authorized, controller-provisioned `ToolWriteGrant` may add a **nested writable bind** for a single `/usr/local/tools/<slug>` installation. Its process must be issued from the verified system rootfs, with a registered `AgentHome`, pinned command, matching agent UID/GID, and active exclusive `shared_tool/<slug>` lease. No guest request can self-approve or extend the unlock.
- The `SharedToolInstallExecutor` keeps the guard active while the supervised child runs. Failed, timed-out, fenced or uncertain operations leave a blocking indeterminate lease; successful exit alone never registers a tool or proves cleanup.
- The operator-supplied `postflight` must independently validate actual writes, expected artifacts, exact bytes and clean routine. Its SHA-256 evidence is recorded separately from the process output receipt. A subsequent `SharedToolStore.register` step remains mandatory.
- `SharedWorkspaceBubblewrapBackend` accepts these grants **only from host-side construction**, never guest environment variables or serialized tool requests. Existing broad-home workspace leases are still required for arbitrary write-capable shells; per-tool locks are cooperative unless the OS mount restrictions qualify on the actual host.

## Acceptance still needed

Run real Linux/WSL2 Bubblewrap checks to prove a normal agent **cannot write any shared tool**, while an operator-unlocked installer can write **only** its own tool. Verify that the unlock disappears after success, failure, timeout, cancellation and operator loss; that another agent cannot reuse the grant; and that activation cannot retain or execute bytes that differ from postflight/re-pinned evidence. Repeat under concurrency, symlink/rename attacks and lease fencing. This increment supplies tests of mount planning, but those are not substitutes for host qualification.
