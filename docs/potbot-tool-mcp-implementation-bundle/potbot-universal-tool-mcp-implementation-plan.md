## 1. Non-negotiable architectural invariants

1. **Canonical semantic identity:** every Type uses an explicit `syn://type/...` or `synny://type/...` URI; instances are distinct from Types. All installed cogs retain required/default/optional Ember semantics.
2. **Separate the stages of authority:** discovery ≠ installation ≠ registration ≠ authorization ≠ execution ≠ verification. Metadata or model-generated text cannot silently grant access.
3. **Cog purity of authorization:** a Cog may transform typed data; even trusted transformation results never automatically authorize tool execution.
4. **Explicit workspaces:** one immutable chosen sandbox root per workspace; host paths outside it are not readable/writable by untrusted workloads. No disguised global downloads.
5. **Custody:** only public verification keys leave the broker; private keys, access tokens and sensitive environment variables never enter model-visible responses, receipts or logs.
6. **Side-effect semantics:** classify operations as read-only, idempotent write, non-idempotent write, destructive; reconcile uncertain outcomes rather than blindly retrying.
7. **Evidence versus assertion:** a syntactically valid response, an MCP success envelope and a passing synthetic test are not sufficient grounds to claim semantic correctness.
8. **Reproducible source:** tool binaries, schema revisions, host qualification, provider versions, input hashes, environment and artifact hashes must be recorded.
9. **Untrusted input:** fetched pages, repository text, issues, tool descriptions, MCP manifests and prompts are untrusted content, never privileged instructions.
10. **Budgeted boundedness:** limits on runtime, tokens, spend, redirects, pages, recursion, concurrency, output size, retries and network access.
11. **Portable but honest:** Windows and macOS launchers may manage dependencies, but untrusted code executes only under a demonstrably qualified containment backend.
12. **Data minimality:** external queries use least disclosure and scoped credentials; every outbound disclosure is assessed by policy.

13. **Event causal provenance:** every typed execution event must identify the authenticated process or immutable input that directly triggered it, as well as the emitting run; no orphan/forged causal edges or inferred authorization.

## 2A. Required SYN event causal tracking and live execution API

**New mandatory requirement:** every execution occurrence (`syn://event/<id>`) must have a resolvable, authenticated **direct trigger**—the process, workflow step, user/API input, schedule occurrence, or external callback that caused it. Every event also records the actual **emitting process**. This applies to start, progress, console output, child tool calls, completion, failure, cancellation and indeterminate outcomes, not merely the first event in a run.

- Start events bind the precise event/subject Type (`syn://type/...` or `synny://type/...`), pinned type/schema version, actual model/workflow/tool implementation or provider revision, unique run UUID, parent-run/step, immutable **typed input parameters** (secure artifact + SHA-256, with a separately redacted public projection), causal trigger and UTC started-at time.
- Progress events carry stage, bounded console/stdout/stderr or typed progress/resource updates, stream chunk identity, original run, emitter and the **specific source process/event** that generated the update.
- Terminal events carry finished-at UTC, elapsed wall-clock milliseconds and timing basis, CPU/RAM/GPU/network/IO/token/cost usage with explicit measured/estimated/unavailable markers, every external tool's unique child-run ID/type/version/receipt, and typed output artifacts with SHA-256; never equate completed generation with independent verification.
- All event identities and links are tenant-scoped, append-only and replayable under the existing PostgreSQL job/evidence stores and commit-ordered WebSocket cursor; do **not** implement a second uncoordinated event stream. Unknown external side effects remain `indeterminate` pending explicit reconciliation. Type declarations must be activated through a reviewed sealed SYN semantic release.
- Extend the existing API with **planned** `/v1/executions`, `/v1/executions/{run_id}`, `/v1/executions/{run_id}/events`, `/v1/executions/{run_id}/tree`, `/v1/events/{event_id}/cause`, and matching authenticated/resumable `/v1/executions/stream` WebSockets. The operator UI must expose active workflow/model/tool timelines and direct cause/input drill-down, subject to authorization and redaction.

**Complete event schema, privacy controls, sequencing, sample start/completion payloads and negative tests:** [Typed live execution monitoring](../implementation/05-syn-execution-monitoring.md). The 48 planned stages are unchanged; requirements are assigned to T01.3, T03.4, T10.2, T10.3, T11.2 and T12.2. This subsection describes **planned work**, not deployed functionality.

## 2B. Universal agent job and MCP workflow coverage (additional mandatory scope)

The unified `syn://event/<uuid>` execution timeline must cover **every job the agent processes**, not only model generation or top-level workflows. Instrument ordinary tools; MCP stdio and Streamable HTTP sessions, MCP tool/resource/prompt operations and nested MCP-composed workflows; agents/subagents; pure Cogs and internal data transformations; scripts/subprocesses; browser, retrieval, API, SQL and CI actions; scheduled and queued maintenance; and future registered agent work types. Each run has a distinct immutable ID, exact SYN subject and Event Type/version, and root or parent input receipt. Every progress/console/child/terminal occurrence has its **actual triggering event/process and emitting process**, including MCP server/session/request correlation, not just a shared parent job ID.

An agent root input can fan out to independent subagent, model, MCP, tool and Cog runs. Each child has its own `run_id`, `parent_run_id`, `parent_event_ref`, immutable typed input and authorized worker/lease provenance; fan-in has explicit contributing input edges. Start/update/completion events track the selected implementation version, precise parameters (private and redacted forms), progress, bounded console/callback output, wall-clock/resource/cost measurements, observed external tool **run IDs** and typed output artifact receipts. Unknown work, remote status and missing measurements must be marked `indeterminate`/`unavailable`, never fabricated.

The existing PostgreSQL `job_events` table requires a concrete `job_id` and **cannot directly persist all standalone executions**. Plan an additive generalized execution-event ledger or equivalent migration that reuses a single transactionally ordered **workspace cursor**, preserves historic job clients, and does not introduce an independent uncoordinated stream. The REST/WebSocket API and dashboard must serve an authenticated, redacted **universal agent-execution tree**, with precise per-event cause and child drill-down independent of transport/protocol.

**Normative scope, MCP correlation model, mixed agent→model→MCP→tool→Cog→subagent example, test matrix and risk controls:** [SYN universal agent-work event specification](../implementation/05-syn-execution-monitoring.md), section 7. These are **requirements for future implementation**, not deployed capabilities. The existing 48 stages and statuses remain unchanged; mandatory work is allocated to T01.3, T02.1–T02.4, T03.4, T10.1–T10.3, T11.2 and T12.2.

## 2C. Phone control, profiling and language-neutral local/remote debugging

Additional mandatory planned scope: Android USB/paired wireless **ADB**; Android native/hybrid control through **Appium/UiAutomator2**; optional **scrcpy** mirroring/input; iOS/iPadOS **XCUITest/WebDriverAgent** on a qualified macOS/Xcode host; and separately qualified emulators/simulators. Include device selection/leases, gestures and text input, app lifecycle, scoped file transfer, logs, screenshots, recordings and outcome readback. Device trust, app/data scope and control effects remain explicit; workspace filesystem isolation alone does not confine a connected phone.

Add bounded profiling capture and analysis for mobile, web and ordinary processes: **Perfetto**, **CDP**, Apple **Instruments/xctrace**, Python profilers and applicable OS/runtime tools. Bind traces, metrics, workloads and comparisons to exact target/build/source identities; record overhead and unavailable counters.

Make process debugging **language neutral** through a common adapter contract, preferring **DAP** where supported and translating other debugger protocols into the same operations. Include launch/attach, verified line/exception breakpoints, conditional/hit-count/function breakpoints when supported, continue/pause, step over/into/out, thread and call-stack inspection, frame selection, locals/arguments/scopes, bounded watches/evaluation, detach and termination. Negotiate language-specific capabilities and reject stale frames after resume. **Implement shared schemas/conformance first, then test the complete workflow with Python/debugpy before qualifying other language adapters.** Python success does not qualify C/C++/Rust, JavaScript/TypeScript, Java, .NET or other backends.

Remote and embedded scope also includes **GDB Remote Serial Protocol**, qualified probe servers (**OpenOCD/pyOCD/probe-rs**), **JTAG/SWD**, and device-specific **ICSP** debugging. Negotiate halt/resume, source/instruction steps, watchpoints, stack/register/memory inspection and core selection. Bind exact probe/target/firmware identities and distinguish debugging from programming, reset, flash and unlock effects. Include **JIT** crash-triggered debugger activation as a separate host/runtime route. Keep the order: local Python first, remote Python next, then a real board/probe fixture and separate ICSP/JIT qualification.

The [detailed device, profiling and debugger specification](../implementation/07-device-control-profiling-debuggers.md) defines the eight-step debugging process, first real Python test, phone/host boundaries, negative cases and stage allocation. ## 2E. Mandatory implementation as SYN Cogs

**Every agent-callable tool operation is a registered SYN Cog**, with one registered typed request envelope as input and one registered typed result envelope as output. MCP, CLI, HTTP, ADB, DAP and other protocols are installed handler implementations beneath this contract. The agent never bypasses the Cog registry to call a transport directly.

The [SYN tool-Cog implementation specification](../implementation/10-syn-tool-cogs.md) defines C01–C07: exact Types/Embers, installed instance and pinned handler binding, out-of-band controller authority for effectful tools, opaque scoped session/async handles, separate transformation/dispatch/execution/verification receipts, conformance, and mandatory per-tool start/progress/completion statistics through the existing [Cog work-monitoring system](../implementation/05-syn-execution-monitoring.md). Each nested or pure Cog has its own run, direct trigger/emitter, bounded actual progress, wall/resource/cost statistics and output/child receipts; unavailable values remain explicit. It maps the existing Cog source contracts and controller gateway, proposes language-neutral debugger request/result Types and describes the complete registered-Cog Python-first test. A binding hash is not source attestation; a transformation result is not execution authority. Existing pure Cogs stay pure; controller-mediated tool execution requires an explicit reviewed runtime extension.

All 48 stages declare `cog_requirements`, and the register retains the mandatory `cog_contract`. Python backend breakpoint/step/stack tests remain useful but full integration requires invoking the installed SYN Cogs through an admitted controller, plus inherited Ember/type/handler/bypass negatives and exact causal receipts. This is a planned architecture requirement, not a claim that those Cogs are already installed.

## 6. Concrete workflow acceptance scenarios

**WF01 — Investigate failing CI:** Given repository/run ID, fetch logs, identify change/exception, inspect source, propose patch in candidate tree, run invariant tests, produce no-merge draft PR. **Pass:** No patch marked verified without unchanged/check-executed manifest; no unapproved GitHub write.

**WF02 — Research uncertain specification:** Search two engines, open original docs, compare publication and retrieval dates, cross-reference, cite exact excerpts, mark unresolved disagreements. **Pass:** Zero fabricated evidence references; contradicted claim remains unresolved.

**WF03 — Browser bug reproduction:** Open isolated browser, capture AX tree, console/network, screenshot and performance trace; local repair proposal and regression test. **Pass:** No session crosses workspace; exact screenshot/trace attached to failure.

**WF04 — Database/API schema reconciliation:** Inspect external API schema and local data schema; compile typed Cog conversions; run read-only join; request approval for any writes. **Pass:** Type incompatibility detected before call; RLS and authorization enforced.

**WF05 — Security design verification:** Translate security invariants into SMT and state-machine models; query Z3, model-check queue transitions; retain counterexamples and unknown states. **Pass:** Deliberately broken dispatch invariant produces counterexample; timeout not called proof.

**WF06 — Resumable parallel research:** Schedule search tasks in parallel; introduce crash after read result and before fan-in; replay run from checkpoint and compare artifact hashes. **Pass:** Consistent events/receipts and no duplicate external write.

**WF07 — Tool package compromise:** Discover malicious MCP manifest with hidden privilege request and tool-injected prompt; attempt install/call; inspect denial and rollback. **Pass:** No access beyond operator-approved scope and no credential leakage.

**WF08 — DanceFlow domain task:** Discover Stemlab/DanceFlow MCP tools and inspect source/fixtures; choose relevant capabilities; generate evidence-backed test/report. **Pass:** Lazy-load song-specific resources, no site-wide asset bloat; one complete receipt chain.

**WF09 — Live workflow/model/tool event trace:** Launch a typed workflow from an authenticated input; stream each unique SYN event with initiating process/input, version, model/tool child run ID, progress and safe output; complete with elapsed time, resource/cost accounting and typed output receipts. **Pass:** every event's exact cause can be inspected, no orphan/cross-workspace edges, lossless replay after restart.

**WF10 — Universal agent/MCP/Cog execution monitoring:** Execute one approved agent workflow that launches a model, a multi-step MCP workflow with nested ordinary API/SQL tool, a typed Cog and delegated subagent, then a queued/scheduled follow-on job. **Pass:** each admitted attempt and update has a unique `syn://event/<id>` and stable locally minted run/child ID, exact event/subject Type/version, source input/process and emitter; replay after worker/API restart reconstructs every nested causal edge, typed output and resource/usage receipt without inventing a completion or repeating side effects.

**WF11 — Android control and recovery:** Select and lease an authorized fixture device by serial, inspect hierarchy, launch the test app, tap/type/scroll, capture screenshot/recording and scoped logs, then disconnect after one action. **Pass:** independent readback, no repeated side effect, no other device/app touched, exact helper/session/forward cleanup.

**WF12 — iOS host qualification:** Run the equivalent native fixture through XCUITest/WebDriverAgent on an authorized macOS/Xcode host and separately record simulator and physical results. **Pass:** exact UDID/build/signing/session scope, real captures, clean teardown; a missing host is an explicit unqualified route.

**WF13 — Language-neutral interactive debugging, Python first:** Use the common debugger contract with Python/debugpy for the first real test. Launch and separately attach to an authorized nested-call fixture; verify line/exception breakpoints; step over, into and out; select two call-stack frames and inspect locals/arguments/scopes; continue to an exception stop; detach or terminate according to ownership. **Pass:** each step waits for its actual stop, frame/value references cannot survive resume or cross targets, source/runtime identity and redacted evidence are retained, and the regression is verified outside the debugger. Other languages reuse the same conformance contract and need their own real fixtures.

**WF14 — Profile a reproducible slowdown:** Capture and analyze a planted CPU/memory/UI hotspot on an authorized target, propose an isolated repair, and compare equivalent workloads with warmup/repetitions and overhead context. **Pass:** hashed raw traces, attributed measurements and bounded local analysis; unavailable counters stay unavailable and instrumentation is separate from baseline timing.

**WF15 — Connected-target remote debugging:** After the first local Python/debugpy test, qualify a scoped remote Python process and one authorized board/probe/firmware route. Select host/probe/core, verify firmware/symbols, halt at a supported breakpoint, inspect stack/registers/permitted memory, step/continue and recover from link loss. **Pass:** stale views and wrong targets denied; no implicit reset, flash, erase or unlock; exact final target state and owned server/session cleanup independently verified. JTAG/SWD, ICSP and JIT routes each require their own supported target/host acceptance.

**WF16 — Workspace files and atomic editing:** Edit two files, inject a concurrent edit and an interrupted commit, then inspect conflict and recovery receipts. **Pass:** A two-file UTF-8/CRLF fixture preserves bytes outside the patch; stale bases and symlink swaps are rejected. Inject failure between commits: recovery restores the old set or completes the journaled new set, and a partial set is never verified. Preview and readback prove the exact resulting hashes. See G01.

**WF17 — Interactive terminal sessions:** Run a local interactive fixture, disconnect once and inspect output, lease expiry and cleanup. **Pass:** An authored interactive child accepts two inputs, resizes and exits; slow output remains bounded. Expired-session input and terminal escape injection fail; cancellation cleans the owned tree. A dropped connection cannot replay a command or claim a prompt was answered. See G02.

**WF18 — Remote development and compute targets:** Inspect a target, transfer a fixture, execute it and verify remote output hashes and teardown. **Pass:** A disposable SSH/container fixture transfers a hash-pinned file and runs a fixed command. Reject changed host keys, wrong cluster/namespace, escaping mounts and stale target leases; cancellation removes only the fixture's processes and forwards. Physical remote-host qualification is recorded independently. See G03.

**WF19 — Network diagnostics and protocol clients:** Diagnose a planted TLS/HTTP fault and compare it with a healthy endpoint using the same policy. **Pass:** A local fixture distinguishes DNS failure, refused connection, expired certificate, redirect denial and slow response. WebSocket reconnect exposes a new attempt without duplicating a write. Capture size/duration is enforced and secret headers/payloads are omitted from receipts. See G04.

**WF20 — Processes, services and operating-system evidence:** Correlate a service error with its process, log window and resource observations. **Pass:** A fixture emits an error and exits; queries locate its exact process and time span. PID reuse cannot redirect a signal; an unrelated service cannot be stopped. Log flooding hits limits without losing a truthful truncation cursor or exposing a planted secret. See G05.

**WF21 — Database transactions, migrations and restore:** Apply and recover a small migration, then show restore evidence from a separate disposable instance. **Pass:** A disposable database passes read/write isolation, stale-row rejection, mid-transaction rollback and lock timeout. Restore a hashed backup into a fresh instance and check schema/data invariants. Lost acknowledgement after commit remains indeterminate until reconciled, without repeating the write. See G06.

**WF22 — Documents, tables, OCR and archives:** Extract a table from an authored PDF, inspect source spans and export a reviewed spreadsheet with a rendered preview. **Pass:** A fixture round-trips Unicode and tabular values, renders a document and traces OCR text to page boxes. Zip traversal, archive bombs, external-link fetches and formula injection are blocked. Report unsupported layout/formula features and compare rendered pages where visual fidelity matters. See G07.

**WF23 — Image, audio and video tool composition:** Inspect an authored short clip and execute one supported transformation with before/after metadata and user-controlled playback. **Pass:** An authored local clip preserves expected duration, sample/frame mapping and caption offsets through a supported adapter. Reject unsupported codecs and oversized inputs explicitly; verify exported bytes and playback separately from a successful render command. No optional model download or paid generation occurs merely on discovery. See G08.

**WF24 — Inbound events, subscriptions and connector writes:** Trigger a workflow from a signed local event, replay it and inspect the single accepted occurrence. **Pass:** A local event source delivers duplicate/out-of-order events and rotates its signing key. Only one admitted workflow is created per canonical occurrence; spoofed and expired events fail. Lost send acknowledgement cannot cause a duplicate; unsubscribe stops new delivery and reports outstanding events. See G09.

**WF25 — Large artifacts, streaming and retention:** Inspect a large trace in bounded pages, reconnect and verify the retained full artifact. **Pass:** Stream an artifact above the inline cap, reconstruct exact bytes by ranges and verify its hash. Disconnect/reorder/duplicate chunks without corruption; reject foreign/expired cursors and changed revisions. Slow consumers stay within declared buffers; retention removes access and reports unavailable historical content honestly. See G10.

**WF26 — Test discovery, coverage and failure reduction:** Select one failing Python case, debug it, rerun outside the debugger and inspect the source-bound test receipt. **Pass:** A Python-first fixture discovers parameterized tests, isolates a planted failure and records source-bound coverage. A seeded property failure reproduces from its minimized input. Changed tests invalidate prior evidence; skipped mandatory cases and a flaky rerun cannot make the original failure disappear. Qualify later language runners independently. See G11.

**WF27 — Debugger completeness and postmortem inspection:** Compare a live Python exception stack with a separately qualified postmortem view; do not claim Python live acceptance qualifies dump formats. **Pass:** Local Python remains first: test breakpoint removal and delayed verification, an actual attach/detach preserving a separately owned fixture, exception stacks and thread selection where supported. Resume invalidates all frame/value handles; mismatched source maps/dumps are rejected. A read-only postmortem fixture cannot resume or mutate a live target. Unsupported async/reverse/native features remain explicit. See G12.

**WF28 — Distributed traces and comparable profiling:** Inspect a causally linked service trace and a reproducible CPU hotspot comparison with measured overhead. **Pass:** A local two-process fixture preserves parent and fan-in links; injected wall-clock skew cannot produce fabricated negative durations or false ordering. Compare the same workload with profiler off/on and report overhead, missing counters and sampled uncertainty. Telemetry exporter failure does not lose execution receipts or authorize retries. See G13.

**WF29 — Reproducible environments and dependency updates:** Recreate a minimal Python tool environment offline and compare its dependency and output identities. **Pass:** A clean offline fixture rebuilds from a pinned cache or reports exact missing artifacts, never downloading silently. Tampered wheels/binaries and incompatible ABI profiles fail before execution. An update/rollback preserves active-run pins and produces the expected source/package hashes; licence restrictions are reported before redistribution. See G14.

**WF30 — Recovery, quotas and operator stop authority:** Cancel a nested workflow during a debugger stop and inspect target, worker, artifact and approval final states. **Pass:** Inject worker death, full scratch storage, dropped cancellation and a stuck child across a bounded workflow. No new effects dispatch after revocation; owned resources reach an observed terminal state or an explicit hold within a configured deadline. Restore a disposable store and reconcile uncertain effects without replay; another tenant's queue remains responsive. See G15.

**WF31 — Operator handoffs and accessible evidence views:** Review a file diff and paused stack, deny one action, then resume an authorized continuation with an auditable receipt. **Pass:** Complete one fixture by keyboard, including deny, cancel and inspection of an indeterminate result. Reject stale/changed approval payloads and cross-workspace links; terminal/HTML artifacts cannot execute in the dashboard. Closing a view does not silently terminate a target or imply cleanup. A handoff resumes exactly once after fresh state validation. See G16.

**WF32 — Core versus specialist gates and traceability:** Render the core dependency path and show that Python-first acceptance can run without Apple, hardware probes, Wolfram or a formal prover. **Pass:** The plan checker verifies 48 unique stages, acyclic explicit hard edges, synchronized Markdown/JSON/CSV, unique gap IDs and complete requirement/fixture coverage. Missing specialist hosts cannot fail an unrelated core profile; an enabled mandatory gate cannot be skipped or declared passed by a mock. No stage status changes merely because requirements were written. See G17.

**WF33 — Typed conversion and discovery lifecycle:** Route a typed table through a unit converter, refresh its tool schema and inspect admission of the next invocation. **Pass:** Reject an ambiguous date/unit conversion, precision loss beyond tolerance, incompatible schema change and an unauthorized server-originated request. A benign discovery refresh does not alter an active run; revocation blocks new dispatch. | Linux sandbox | Every PR in security CI | Bubblewrap/seccomp, filesystem, network broker, process kills | Host preflight qualified, then all negative cases denied |
| Windows/macOS launcher | Every PR/profile change | uv, bootstrap, local assets, process-isolation qualification or fail-closed | No unqualified execution of untrusted tools |
| E2E offline | Every PR/nightly according to cost | Local controlled Git/SQL/MCP/browser/solver workflows | Deterministic golden workflows pass |
| Device/debug contract | Every affected adapter/profile PR | Hardware-free ADB/Appium/DAP fixtures, target/session/stop identity, stale handles, disconnect and effects | Shared contract passes; no false real-device or language acceptance |
| Real device/debug host | Opt-in qualification of each enabled profile | Android/iOS devices, emulators/simulators, actual profiler/debugger backend; Python/debugpy first | Exact qualified host and evidence; named unavailable routes never silently pass |
| Adversarial/chaos | Nightly and release | Prompt injection, SSRF, symlink races, replay, credential theft | Zero known critical escape, signed report |
| Live vendor smoke | Opt-in scheduled and release | Approved providers, capped spend, scoped tokens, reliable API availability | Report pass/fail/unavailable; no automatic false qualification |
| Reasoning A/B | Nightly/release | Same tasks model-only vs tool/critic/solver profiles | Comparable metrics with confidence intervals, no synthetic/live mixing |

### Release-wide acceptance targets

- **Security:** 0 successful critical cross-workspace read/write, host filesystem escape, credential exfiltration or unauthorized destructive calls in a pinned adversarial corpus. These are pass/fail gates; absence of known failures is not proof of universal security.
- **Execution:** 0 unapproved duplicate side effects in deliberately injected crash windows, with ambiguous external outcomes represented as `unknown`/`needs-reconciliation` rather than `success`.
- **Integrity:** 100% of claims marked `verified` have acceptable evidence receipts under the versioned scoring policy; mutated receipts and source hashes are rejected.
- **MCP:** ≥95% conformance pass on agreed deterministic fixtures, with all critical protocol/auth cases passing; unsupported optional capabilities explicitly declared.
- **Browser:** ≥95% fixture-task success in qualified environment and zero cross-profile cookies/session leaks; provider-specific reliability is separately reported.
- **Routing:** ≥90% class-level recall@3 on a versioned 40-task capability-matching golden suite initially, raised after baseline measurements; 0 policy-forbidden executable selections.
- **Reasoning:** report paired verified success, false positive, failure, token+money cost and latency against model-only, per task family; improvement is an empirical decision gate rather than an assumed result.
- **Durability:** every workflow node transitions through valid states; event replay and immutable artifacts survive abrupt worker termination.
- **Live observability:** 100% of started/updated/output/tool/terminal events in qualified fixtures have a typed versioned `syn://event/<id>` occurrence, exact run identity, authenticated initiating process or input, emitting process, replay-safe causation and redacted data projection; terminal events retain measured/estimated/unknown wall-clock, resource, tool-run and output receipt data.
- **Device and debugging:** each enabled phone or language adapter passes common target/scope, lifecycle, effect and evidence contracts plus its own real-host fixture. Python/debugpy is the first full breakpoint/stepping/stack test; unsupported backends and missing physical hosts remain explicitly unqualified.
- **Deployment:** fresh qualified host setup and rollback validated; unqualified hosts fail closed for dangerous operations.

Targets are proposed gates to calibrate against realistic task difficulty and reproducibility, not measurements of the current repository.

### Benchmark methodology

Freeze task and grader versions; report pass@1/pass@k, confidence intervals (paired/bootstrap or exact binomial as appropriate), false-verified rate, clarification/unknown rate, wall-clock time, input/output tokens, paid API cost, egress bytes, retry count, success per unit cost and unsafe-call counts. Compare only runs with the same evaluator and pinned task split. Track model/provider/temperature/seed when supported, context packet hash, tool versions, external service availability and host isolation state. Benchmarks with intentionally constructed patches are **orchestration tests** rather than estimates of reasoning quality.

## 8. Standard stage-gate report JSON schema

Store a stage outcome and a traceable link to reports under `docs/implementation/tool-integration/gates/`. Suggested form:

```json
{
  "stage_id": "T03.4",
  "source_commit": "<full sha>",
  "schema_revision": "tool-gate-v1",
  "host_qualification": "linux-bwrap-qualified",
  "state": "passed|failed|blocked|not-run",
  "checks": [
    {
      "name": "no-double-dispatch",
      "status": "passed",
      "evidence": "artifact://...",
      "suite": "integration"
    }
  ],
  "migration_revision": "<revision>",
  "policy_digest": "<sha256>",
  "evidence_manifest_sha256": "<sha256>",
  "blocking_defects": [],
  "authorizations": {
    "credentialed_live_tests": false
  }
}
```

A stage only passes when all mandatory checks ran and passed. An absent host prerequisite yields `blocked`, **never** `passed` or a silent skip. Gates are immutable once published; subsequent requalification creates a new report.

Prefer **one PR per stage**, subdividing risky stages into narrow implementation PRs but preserving a single explicit acceptance gate. Each PR description references exactly one primary stage and can identify prerequisites. Do not merge implementation-specific features from concurrent chats without rebasing and re-running relevant gates on a single pinned commit.

## 13. Programme risk register and stage estimates

Estimates below are rough **engineering-week ranges for focused workstreams**, not delivery dates or promises. Several streams can run in parallel after the P03 security boundary has been qualified. Reuse/extension findings from T01.1 may lower effort significantly; credentialed vendor qualification and Windows/macOS isolation may increase it.

| Phase | Rough engineering weeks | Primary uncertainty | Mitigation |
|---|---:|---|---|
| P01 | 2–4 | Existing scheme collisions | Inventory-first and codeowner review |
| P02 | 3–6 | MCP protocol/version compatibility | Official SDK, fixture matrix and negotiated versions |
| P03 | 4–8 | Containment, credentials, crash/replay semantics | Fail closed, qualified Linux host, fault injection |
| P04 | 3–5 | Untrusted registry metadata and churn | Quarantine/discovery separation and pinned manifests |
| P05 | 3–6 | Search quota, parsing quality, rights | Multiple provider adapters and source-artifact hashes |
| P06 | Re-estimate expanded scope | Browser/phone isolation, host signing and physical-device variability | Separate target leases, local fixtures and per-host acceptance |
| P07 | Re-estimate expanded scope | Language-neutral debugging/profiling plus PR state races | Shared conformance first, real Python test next, per-language qualification |
| P08 | 3–6 | RLS, provider schemas and external auth | Read-only defaults and generated contract tests |
| P09 | 4–7 | Formalization mistakes and solver timeouts | Typed results, independent checkers and unknown status |
| P10 | 4–8 | Durable side effects and scheduler integration | Reuse existing job/store and state machine testing |
| P11 | 3–6 | Evaluator bias and benchmark contamination | Blind hold-out, preregistered tasks and paired runs |
| P12 | 2–5 | Packaging and multi-platform qualification | Pinned install, explicit host support matrix |

| Risk | Severity | Trigger | Mandatory response |
|---|---|---|---|
| Unsafe MCP server or compromised package | Critical | Manifest adds scopes or executable binary changes | Quarantine instance, revoke install, run forensic receipt audit |
| Workspace escape / host access | Critical | Any successful boundary-crossing fixture | Stop release; fix isolation; rerun full adversarial suite |
| Private credential leakage | Critical | Token/private key appears in model context/log/artifact | Disable credential, rotate, incident-review, add regression |
| Duplicate non-idempotent action | Critical | Crash/restart repeats external write | Quarantine uncertain outcome; add reconciliation; fix state machine |
| Misleading benchmark improvement | High | Synthetic/live mixed or scorer changes | Invalidate comparison; rerun with frozen task+grader |
| Tool discovery overload | Medium | Planning latency/token use exceeds cap | Lazy tool metadata and cost-aware capability ranking |
| Unbounded provider costs | High | Retry/parallel plan exceeds budget | Enforce budget before reservation/dispatch; halt run |
| Drifting external APIs | Medium | Schema/endpoint differs from pinned contract | Quarantine adapter revision and require qualification |
| Concurrent changes in Potbot | High | Overlapping migrations/contracts/phase work | Rebase pinned SHA and execute upgrade/full CI |
| Wrong phone/process or stale stopped frame | Critical | Device/PID/lease changes, resume or debugger disconnect | Deny stale actions, invalidate frame handles and reconcile exact target state |

**Suggested ownership:** one core semantics/DB owner, one execution/security owner, one integration/adapters owner, one evaluation/CI owner, and reviewers familiar with the existing Cog and identity architecture. External API cost and policy approval remains an operator responsibility. Resist adding a separate workflow scheduler or second authority engine simply for convenience.

## 14. Definition of done for the complete programme

The programme is complete only when: (a) all 48 stage-gate reports are passing or have explicitly approved documented scope reductions; (b) real qualified-host PostgreSQL, sandbox, API, browser, tool, reasoning and adversarial tests pass; (c) the agent autonomously discovers and composes authorized tools through typed cogs while preserving the boundaries between discovery, transformation, execution and verification; (d) benchmark data establishes real rather than assumed reasoning benefits; (e) enabled phone, profiling and language-neutral debugging profiles pass the device/process gates and actual Python-first breakpoint/stepping/stack test, with separate acceptance for other backends; and (f) a reproducible tagged release with upgrade/rollback instructions and known limitations is published.

**Foundation entry point (historical programme ordering):** Implement `T01.1` on a fresh pinned repository branch: emit the current-state inventory JSON, produce a code-to-stage traceability map, identify missing/duplicate components, and add an automated consistency test. No production code changes should be required in that first PR.
